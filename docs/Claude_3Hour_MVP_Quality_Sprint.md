# Claude Code 실행 문서 — StudyLog 3시간 MVP 품질 스프린트

> 이 문서는 Claude Code가 StudyLog 저장소에서 약 3시간 동안 자율적으로 분석, 수정, 테스트까지 수행하도록 만든 실행 프롬프트다.

## 실행 방법

Claude Code를 StudyLog 프로젝트 루트에서 연 뒤 아래 한 문장만 입력한다.

```text
docs/Claude_3Hour_MVP_Quality_Sprint.md를 처음부터 끝까지 읽고, 적힌 순서와 제한을 지키면서 작업을 실제로 수행해줘. 분석이나 계획만 제출하고 멈추지 말고, 안전하게 구현 가능한 항목은 구현·테스트·정리까지 계속 진행해. 기존 사용자 데이터와 기능을 보존하고, 완료 후 보고서를 작성해줘.
```

---

# 1. 역할과 목표

당신은 StudyLog의 시니어 프론트엔드 엔지니어, QA 엔지니어, 제품 UX 엔지니어다.

이번 작업의 목표는 새로운 대형 기능을 무작정 추가하는 것이 아니다. 현재 MVP의 핵심 순환을 실제 출시 가능한 수준으로 단단하게 만드는 것이다.

```text
앱 진입
→ 과목 생성
→ 공부 시작
→ 공부 종료 및 보상
→ 오늘의 퀘스트 진행/수령
→ 캐릭터 성장 확인
→ 결과 카드 캡처/공유
→ 상점/시즌 보상 확인
```

이 흐름에서 사용자가 막히거나, 상태가 서로 다르게 보이거나, 모바일 화면이 깨지거나, 새로고침 후 데이터가 사라지는 문제를 찾아 고친다.

StudyLog의 제품 원칙은 다음과 같다.

- 통계보다 캐릭터가 먼저 보여야 한다.
- 생산성 대시보드보다 귀여운 공부 RPG처럼 느껴져야 한다.
- 공부 종료 후 성장과 공유까지 자연스럽게 이어져야 한다.
- 사용자가 실제로 하지 않은 공부, 획득하지 않은 보상, 달성하지 않은 업적을 만들어내지 않는다.
- 사용자의 기존 기록과 구매·착용 상태는 최우선으로 보존한다.

# 2. 시작 전에 반드시 할 일

코드를 수정하기 전에 다음을 수행한다.

1. `git status --short --branch`로 현재 브랜치와 변경 사항을 확인한다.
2. 사용자가 만든 미커밋 변경이 있다면 절대 덮어쓰거나 되돌리지 않는다.
3. `package.json`의 실제 스크립트를 확인한다.
4. `src/App.tsx`부터 Home, Timer, Reward, Daily Quest, Capture, Shop, Profile의 렌더링 경로를 추적한다.
5. Zustand persist store의 저장 키와 데이터 구조를 확인한다.
6. 아래 기준 검사를 실행해 시작 상태를 기록한다.

```bash
npm run lint
npm test -- --run
npm run build
npm run validate:assets
```

검사가 실패하면 이번 작업으로 인한 실패인지 기존 실패인지 구분해서 기록한다.

분석 후 계획만 말하고 멈추지 않는다. 영향 범위가 확인되면 바로 구현 단계로 진행한다.

# 3. 절대 수정 금지 및 안전 규칙

다음은 명시적인 근거 없이 변경하지 않는다.

- Supabase 데이터베이스 스키마
- API 요청 형식과 서버 계약
- 인증 방식
- 기존 타이머의 시간 측정 원칙
- 기존 포인트 거래 기록 구조
- 사용자 과목 및 공부 세션 데이터 구조
- 기존 상점 구매 기록과 착용 데이터
- 이미지 에셋 파일명 규칙
- 캐릭터 whole-avatar 및 baked full-scene 렌더링 정책
- 라우팅·화면을 제거하거나 기존 기능을 숨기는 변경

다음 행동은 금지한다.

- `git reset --hard`, 강제 checkout, 사용자 변경 삭제
- 테스트를 지우거나 약화해서 통과시키기
- 오류를 `any`, 무조건적인 타입 단언, 빈 catch로 숨기기
- 기존 상태 관리 전체 재작성
- 새로운 외부 라이브러리 설치
- 새로운 AI/API 기능 추가
- 새 이미지 생성 또는 기존 캐릭터 이미지 변형
- 미완성 레이어 합성 시스템 부활
- 허위 공부 기록, 허위 랭킹, 허위 보상 생성
- 검증 없이 대규모 폴더 구조 변경
- 사용자 승인 없이 원격 push 또는 배포

필요한 파일만 수정하고, 변경은 작고 추적 가능하게 유지한다.

# 4. 작업 우선순위

시간이 부족할 경우 P0부터 끝내고 P1, P2 순서로 진행한다. P0 검증이 끝나지 않았는데 P2로 넘어가지 않는다.

## P0 — 핵심 사용자 흐름 및 데이터 안전성

### 4.1 신규 사용자 흐름

다음 흐름을 코드와 UI 기준으로 점검하고 발견한 문제를 수정한다.

1. 온보딩 완료
2. 과목이 없는 상태
3. 첫 과목 생성
4. 생성한 과목 자동 선택
5. 타이머 시작
6. 일시정지/재개
7. 타이머 종료
8. 세션 저장
9. 포인트 및 Study XP 적립
10. 보상 모달 표시
11. Capture 화면 이동

확인 사항:

- 중복 클릭으로 타이머나 세션이 두 번 생성되지 않는가?
- 과목 없이 시작할 때 조용히 실패하지 않고 이유를 알려주는가?
- 종료 직후 Home, 퀘스트, 레벨, Capture가 같은 데이터를 보여주는가?
- 새로고침 후 과목, 세션, 포인트, 착용 상태가 유지되는가?
- 아주 짧은 세션이 Study XP/출석 규칙을 잘못 뚫지 않는가?

### 4.2 일일 퀘스트 안정성

현재 구현된 오늘의 퀘스트를 검토한다.

- 오늘 날짜의 실제 세션만 진행도에 반영
- 첫 기록, 30분 집중, 서로 다른 과목 2개 조건 정확성
- 완료 전 수령 불가
- 완료 후 한 번만 수령
- 새로고침 후 수령 상태 유지
- 날짜 변경 시 이전 수령 상태가 오늘을 막지 않음
- 퀘스트 보상 포인트가 Study XP나 시즌 XP로 잘못 계산되지 않음
- 보상 수령 직후 포인트 UI가 즉시 갱신

중복 수령, 날짜 경계, stale persisted state 관련 회귀 테스트가 부족하면 추가한다.

### 4.3 달빛 시즌 안정성

- 실제 Study XP만 시즌 진행도에 반영
- 10/45/90 XP 보상 조건 정확성
- 각 보상 한 번만 수령
- 최종 스킨 지급 및 착용 상태 일치
- 이미 스킨을 보유한 사용자에게 대체 80P 지급
- 스킨 지급/착용이 Home, Timer, Capture, Shop에 동일하게 반영
- 이전 persisted store 데이터가 최신 catalog를 가리지 않음

보상 지급 도중 일부 상태만 반영되는 경로가 없는지 확인한다.

### 4.4 Capture/Share 안정성

- 현재 착용 캐릭터와 전체 방 스킨이 Capture에도 반영
- 레벨/메시지가 일러스트를 가리지 않음
- 정사각형과 9:16 모두 필수 정보가 잘리지 않음
- 공유 카드 테마 잠금 조건 정확성
- 이미지 생성 실패/시간 초과 후 버튼이 영구적으로 잠기지 않음
- 연속 클릭으로 여러 캡처 작업이 동시에 실행되지 않음
- 브라우저가 파일 공유를 지원하지 않을 때 저장 fallback 정상 작동

Capture 동작을 고칠 때 카드 밖 UI가 생성 이미지 안으로 들어가지 않도록 주의한다.

## P1 — 모바일 UX와 일관성 개선

### 4.5 Home 화면 계층

다음 우선순위를 유지한다.

```text
캐릭터/방
→ 공부 시간과 시작 버튼
→ 오늘의 퀘스트
→ 성장 요약
→ 보조 통계
```

확인 사항:

- 320px, 375px, 390px, 430px에서 가로 스크롤 없음
- 고정 프로필/알림/BGM/하단 내비게이션이 콘텐츠를 가리지 않음
- 터치 대상 최소 44px 권장
- 버튼 disabled 상태가 이유 없이 보이지 않음
- 빈 상태가 다음 행동을 한 문장과 하나의 주요 버튼으로 안내
- 캐릭터 카드가 통계 카드보다 시각적으로 강함
- 퀘스트 보드 텍스트가 작은 화면에서 지나치게 작거나 잘리지 않음

기존 StudyLog의 크림, 핑크, 살구, 라벤더 색상과 둥근 Nintendo풍 카드를 유지한다. Material Dashboard처럼 바꾸지 않는다.

### 4.6 상태 피드백

다음 행동에 즉각적인 피드백이 있는지 확인하고, 부족하면 기존 디자인 시스템 안에서 작은 개선을 한다.

- 과목 생성 성공/실패
- 타이머 시작/일시정지/종료
- 퀘스트 보상 수령
- 시즌 보상 수령
- 상점 구매/착용/해제
- 이미지 저장/공유 성공 또는 실패

브라우저 alert 남발은 피한다. 기존 컴포넌트 패턴이나 작고 접근 가능한 인라인 상태를 선호한다.

### 4.7 접근성 기본 점검

- icon-only 버튼에 실제 `aria-label` 존재
- 진행 막대에 label, min, max, current 존재
- 모달/오버레이 닫기 버튼 명확성
- 키보드 focus-visible 유지
- 색상만으로 완료/잠금 상태를 전달하지 않음
- 장식용 이모지와 이미지가 스크린리더 노이즈를 만들지 않음
- heading 순서가 지나치게 깨지지 않음

접근성을 위해 디자인 정체성을 없애지 않는다.

## P2 — 성능과 코드 품질

P0/P1이 완료되고 시간이 남는 경우에만 수행한다.

### 4.8 렌더링 및 구독 점검

- Zustand selector가 매초 불필요한 전체 화면 렌더링을 만드는지 확인
- 타이머 tick이 무거운 통계/퀘스트/상점 컴포넌트를 불필요하게 다시 그리는지 확인
- 렌더 함수 안의 큰 계산 중 실제로 memoization 가치가 있는 것만 최적화
- lazy-loaded secondary screen 구조 유지
- 이미지 로드 실패 fallback 유지

근거 없는 `useMemo`, `useCallback`, `React.memo` 도배는 하지 않는다. 실질적인 렌더 경로가 확인된 경우에만 적용한다.

### 4.9 코드 중복과 테스트 가능성

- 날짜/보상/진행률 계산이 UI 컴포넌트에 중복되어 있다면 작은 pure function으로 분리
- store action의 중요한 조건은 pure function 또는 store 테스트로 보호
- CSS/Tailwind 문자열을 과도하게 추상화하지 않음
- 현재 프로젝트 스타일을 따른다

# 5. 테스트 요구사항

수정한 동작마다 최소한의 회귀 테스트를 추가한다. 특히 다음 경계를 우선한다.

- 정확히 30분인 퀘스트와 29분 59초인 퀘스트
- 같은 과목 세션 2개와 서로 다른 과목 세션 2개
- 날짜가 다른 세션
- 이미 수령한 일일/시즌 보상
- persisted 날짜가 어제인 상태
- 이미 달빛 스킨을 보유한 최종 시즌 보상
- 이미지 경로가 없거나 로딩 실패하는 캐릭터 fallback
- 빈 과목 목록과 archived 과목

테스트는 실제 규칙을 검증해야 하며 구현 세부사항만 복제하지 않는다.

# 6. 실행 중 의사결정 규칙

## 바로 수정해도 되는 것

- 명백한 UI 잘림/겹침
- 잘못된 disabled 상태
- 실제 데이터와 다른 표시
- 중복 보상/중복 세션 위험
- persistence merge 오류
- 접근성 label 누락
- 테스트로 재현 가능한 예외 처리 오류
- 작은 화면의 가로 스크롤

## 문서에만 기록하고 구현하지 말아야 하는 것

- DB 스키마 변경이 필요한 기능
- 운영 정책이 필요한 학교 인증/랭킹 보상
- 실제 결제 도입
- AI API 도입
- 새로운 이미지 에셋이 필요한 캐릭터·스킨
- 제품 방향을 바꾸는 대형 내비게이션 개편
- 현재 데이터와 호환되지 않는 상태 관리 재설계

확실하지 않은 문제를 추측으로 고치지 않는다. 재현 근거가 없으면 최종 보고서의 제안 항목으로 남긴다.

# 7. 검증 순서

작업 후 반드시 아래 순서로 검증한다.

```bash
npm run lint
npm test -- --run
npm run build
npm run validate:assets
git diff --check
```

가능하면 로컬 앱을 실행해 다음 뷰포트를 확인한다.

- 320 × 568
- 375 × 667
- 390 × 844
- 430 × 932

수동 확인 흐름:

1. 빈 신규 사용자 상태
2. 과목 생성
3. 타이머 시작/일시정지/재개/종료
4. 보상 모달
5. 일일 퀘스트 진행 및 수령 가능 상태
6. Capture 정사각형/스토리 전환
7. 상점 미리보기/착용
8. 시즌 카드
9. 마이페이지 배지 컬렉션
10. 새로고침 후 상태 유지

테스트를 위해 기존 사용자의 실제 브라우저 데이터를 지우지 않는다. 별도 로컬 세션이나 테스트 데이터로 확인한다.

# 8. 시간 운영 가이드

정확한 타이머를 맞추기보다 다음 비율로 작업한다.

## 0~30분

- 저장소/상태/핵심 흐름 분석
- 기준 검사 실행
- 수정할 문제를 P0/P1/P2로 분류

## 30~110분

- P0 문제 재현 및 수정
- 각 수정에 회귀 테스트 추가
- 중간 lint/test 실행

## 110~155분

- 모바일 UX, 빈 상태, 피드백, 접근성 개선

# 9. 완료 조건

다음 조건을 모두 만족해야 완료로 보고한다.

- 기존 핵심 기능 삭제 없음
- 기존 공부 기록/과목/포인트/구매/착용 데이터 구조 보존
- 확인된 P0 문제 해결 또는 재현되지 않음을 근거와 함께 기록
- 수정한 모든 로직에 필요한 테스트 존재
- TypeScript build 통과
- lint 통과
- 전체 test 통과
- production asset validation 통과
- `git diff --check` 통과
- 320px 모바일에서 가로 스크롤 없음
- 불필요한 새 의존성 없음
- 임시 파일, 디버그 UI, console 로그 없음

검증이 실패한 상태에서 완료라고 말하지 않는다.

# 10. Git 규칙

- 시작 시 사용자의 미커밋 변경을 보존한다.
- 관련 없는 파일을 수정하지 않는다.
- 생성된 `dist`를 커밋하지 않는다.
- 테스트를 통과한 뒤 변경 파일을 다시 확인한다.
- 사용자가 따로 지시하지 않았다면 `git push`와 배포는 하지 않는다.
- 커밋할 경우 하나의 명확한 커밋으로 만들고 커밋 해시를 보고한다.

권장 커밋 메시지:

```text
fix: harden StudyLog MVP user journey
```

# 11. 최종 보고서

작업이 끝나면 프로젝트에 다음 파일을 작성한다.

```text
docs/Claude_3Hour_MVP_Quality_Sprint_Report.md
```

보고서에 반드시 포함할 내용:

1. 시작 시 저장소 상태
2. 실제로 재현한 문제
3. 수정한 문제와 사용자 영향
4. 변경 파일 목록
5. 추가/수정한 테스트
6. 실행한 검증 명령과 결과
7. 모바일 확인 결과
8. 구현하지 않고 보류한 항목과 이유
9. 다음 작업 추천 3개 이하
10. 커밋 여부와 커밋 해시

최종 채팅 답변은 다음 순서로 간결하게 작성한다.

```text
결과 요약
핵심 수정
검증 결과
남은 위험
변경 파일
커밋 정보
```

분석만 하고 끝내지 말고, 안전한 범위에서 구현과 검증까지 최대한 진행한다.
