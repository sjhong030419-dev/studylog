# Claude Code·Codex 공통 작업 규칙

## 1. 작업 시작 전

1. 요청 내용을 정확히 읽고 작업 범위를 한 문장으로 정리한다.
2. `docs/PROJECT.md`, `docs/DESIGN.md`, `docs/ROADMAP.md`, `docs/RULES.md`를 확인한다.
3. 관련 파일과 현재 구현을 먼저 읽는다.
4. `git status`를 확인하고 기존 변경사항을 사용자의 작업으로 취급한다.
5. 범위 밖의 리팩터링이나 기능 변경은 하지 않는다.

## 2. 역할 분담

### Claude Code

- 합의된 요구사항에 따라 기능과 UI를 구현한다.
- 작업 전에 수정할 파일과 접근 방식을 간단히 알린다.
- 기존 동작을 유지하면서 필요한 범위만 변경한다.

### Codex

- Claude Code 또는 사용자가 만든 변경사항을 먼저 검토한다.
- 버그, 회귀, 타입 오류, 모바일 UI, 접근성, 성능, 중복 코드를 확인한다.
- 리뷰 요청일 때는 명확한 허가 없이 파일을 수정하지 않는다.
- 수정 요청일 때는 확인된 문제만 최소 범위로 고친다.

한 에이전트가 작업 중일 때 다른 에이전트가 같은 파일을 동시에 수정하지 않는다.

## 3. 코드 변경 원칙

- 기존 기능, 데이터, 설정을 임의로 삭제하지 않는다.
- 사용자가 요청하지 않은 전체 구조 변경이나 대규모 리팩터링을 하지 않는다.
- 기존 컴포넌트, 타입, 상태 관리 패턴을 먼저 재사용한다.
- TypeScript 타입 안전성을 유지하고 불필요한 `any`를 추가하지 않는다.
- 비밀키, 토큰, 개인정보를 코드나 문서에 넣지 않는다.
- `.env`의 실제 값은 출력하거나 커밋하지 않는다.
- 앱 이탈 감지, 타이머, 통계처럼 시간에 민감한 기능은 경계 조건을 확인한다.
- 서버 또는 Supabase 데이터 구조 변경이 필요하면 영향과 마이그레이션을 먼저 설명한다.

## 4. 디자인 변경 원칙

- 모바일 화면을 먼저 확인한다.
- 도트 감성과 캐릭터 중심의 정체성을 유지한다.
- 캐릭터의 크기만 키우는 것이 아니라 시간, 버튼, 상태 문구와의 시각적 균형을 맞춘다.
- 기존 색상, 간격, 카드, 버튼 패턴을 우선 재사용한다.
- 로딩, 오류, 빈 상태, 다크 모드를 함께 고려한다.
- 접근 가능한 이름, 키보드 조작, 색상 대비를 해치지 않는다.

## 5. 검증 기준

변경 범위에 맞게 다음을 확인한다.

```bash
npm run lint
npm run build
```

필요하면 개발 서버에서 관련 화면을 직접 확인한다.

- 타이머 시작·일시정지·재개·종료
- 화면 이동, 새로고침, 앱 이탈 후 상태
- 작은 모바일 화면과 긴 문구
- 데이터가 없을 때와 오류가 발생했을 때
- 다크 모드
- 친구방 연결·해제와 실시간 상태

검증을 실행하지 못했거나 실패했다면 숨기지 말고 이유와 남은 위험을 보고한다.

## 6. Git과 변경사항 보호

- 기존의 커밋되지 않은 변경사항을 되돌리거나 덮어쓰지 않는다.
- 사용자의 명시적 요청 없이 커밋, 푸시, 브랜치 삭제, 배포를 하지 않는다.
- 자동 생성 파일이나 관련 없는 파일을 불필요하게 변경하지 않는다.
- 충돌 가능성이 있으면 작업을 멈추고 사용자에게 알린다.

## 7. 완료 보고

작업이 끝나면 다음을 간단히 보고한다.

1. 무엇을 변경했는지
2. 생성·수정한 파일
3. 실행한 검증과 결과
4. 확인하지 못한 항목이나 남은 위험

완료 기준을 충족하지 못한 작업을 완료했다고 표현하지 않는다.

## 8. 판단이 필요한 경우

- 문서보다 사용자의 최신 명시적 요청이 우선한다.
- 요구사항이 서로 충돌하거나 데이터 손실 위험이 있으면 추측하지 말고 확인한다.
- 사소하고 되돌릴 수 있는 세부사항은 기존 프로젝트 관례에 맞춰 합리적으로 결정한다.
